# user_working

> Claude Code skill —— 我（用户）的个人开发协作规范：怎么理解我的需求 + 开发过程习惯与规范。

## 解决什么问题

我作为用户，**不是技术专家**：我的需求可能模糊、不准确、甚至带专业错误。直接照字面执行会做出错的东西。这个 skill 告诉 agent：

1. **怎么理解我的需求**：把我当"什么都不会的傻子"，用产品经理思维先理解"我到底要什么、为什么、谁用、什么场景用"，再动手。我的话是**需求信号**，不一定是**实现指令**。
2. **开发过程的规范**：开发前先规划拆分、反过度设计、非破坏性写入、数据展示永不截断、完工后多角度 review。这些来自 autopilot 沉淀的运行 / review 规范，现在也适用于日常开发。

## 核心特性

- **产品经理思维理解需求** —— 复述理解、识别缺口、主动补全，而不是照字面执行
- **开发前规划** —— 功能拆分、复用检查、依赖识别、风险预判
- **反过度设计** —— YAGNI、三次法则、不过早优化、最小可行改动
- **业务参数外置** —— 业务可变或多处耦合的参数（阈值 / 限额 / 开关条件）集中放配置、带注释、单一来源；与 YAGNI 划清边界，纯技术常量不外置
- **非破坏性写入** —— 不可再生产物只新增、不覆盖
- **数据展示永不截断** —— 完整展示，分页 / 外化文件而非截断
- **完工后多角度 review** —— 功能完备性、用户直觉、冲突检测、测试完备性等 11 个角度
- **结构化汇报** —— 做了什么 / 关键决策 / 测试 / 待确认 / 额外说明

### 业务参数外置（降低后期人工维护成本）
凡是**随业务需求可能变动**的参数（阈值、限额、天数、开关条件……），不散落成魔法数字，集中放到一处便于人工快速修改的配置位置：优先复用项目既有 config 入口，没有再新建**唯一**集中处、按功能域分组；每个参数带注释（含义 / 单位 / 影响面），多处引用同一配置项、不复制字面量；密钥走 `.env` 不与业务参数混放。**与 YAGNI 的边界**：外置的是"有真实业务语义、可预期变动"的参数；纯技术常量（分页大小、重试次数）就地命名即可，不为想象中的未来预建配置开关。判定：业务可变 OR 被 ≥2 处引用，满足其一即外置。完工 review 顺带治理本次改动里的存量魔法数字。

## 使用

```
/user_working
```

触发后，agent 会：
1. 以产品经理思维理解你的需求（复述理解 + 关键问题）
2. 开发前做规划拆分
3. 按反过度设计原则开发
4. 完工后从多角度 review
5. 给出结构化汇报（含"额外说明"方便你纠正）
